# 压测报告

测试时间：2026-10-13　23:40 ~ 23:42
工具：`ab`（macOS 自带 Apache Bench）+ `docker stats` 后台采样
压测对象：shortlink 单实例应用（Spring Boot 3 / Java 17 / JVM `-Xms256m -Xmx512m`）
基础设施：App + Redis 7 + MySQL 8 + Kafka 3.9，全部运行于本地 Docker

## 1. 测试环境

| 组件 | 配置 |
|------|------|

**前置条件**：测试期间临时把 `redirect-limit` 放宽到 1,000,000、`create-limit` 放宽到 100,000（避免单 IP 压测撞上限流），测试结束已恢复（120 / 5）。

## 2. 测试场景

| 场景 | 路径 | 描述 | 并发 | 时长 |
|------|------|------|------|------|
| **S1 跳转命中** | `GET /{code}` | 主热路径，code 已在 Redis（缓存命中） | 50 / 100 / **150** / 200 | 30s × 3 + 失败 1 次 |
| **S2 创建短链** | `POST /api/v1/links` | 写路径：限流 → 雪花 ID → Base62 → MySQL INSERT → Redis SET | 20 | 30s |

| **S4 跳转未命中** | `GET /{未知 code}` | 404 路径：Redis miss → MySQL → 空值占位 | 100 | 30s |

每场景独立测试。同一短链 `MiFqiunndr` 用作 S1 / S3 的目标，**先做 5s / 50 并发预热**确保缓存命中。

## 3. 压测结果

### 3.1 S1 跳转命中（阶梯并发）

| 并发 | RPS | p50 | p90 | p95 | p99 | 最长 | 错误 |
|---:|---:|---:|---:|---:|---:|---:|---:|
| 50  | 3,240  | 13 ms | 27 ms | 35 ms | 62 ms | 170 ms | 0 / 50,000 |
| 100 | 5,181  | 17 ms | 31 ms | 37 ms | 61 ms | 121 ms | 0 / 50,000 |
| 150 | 6,016  | 22 ms | 38 ms | 46 ms | 70 ms | 165 ms | 0 / 50,000 |
| 180 | — | — | — | — | — | — | `Connection reset by peer` |
| 200 | — | — | — | — | — | — | `Connection reset by peer` |

**RPS 增益**：50→100 +60%，100→150 +16%（接近饱和）。  
**延迟曲线**：p50 从 13ms 涨到 22ms（+69%），p99 从 62ms 涨到 70ms（+13%）——排队开始但尚未失控。  
**错误率**：全部为 0，直到 c=180。

### 3.2 S2 / S3 / S4

| 场景 | 并发 | RPS | p50 | p90 | p95 | p99 | 最长 | 错误 |
|------|---:|---:|---:|---:|---:|---:|---:|---:|
| **S2 创建短链** | 20 | 530 | 21 ms | 36 ms | 44 ms | 72 ms | 6,729 ms | 0 / 15,955 |
| **S3 统计查询** | 50 | 533 | 23 ms | 66 ms | 380 ms | 894 ms | 6,798 ms | 0 / 16,337 |
| **S4 跳转未命中** | 100 | 538 | 27 ms | 392 ms | 1,118 ms | 1,260 ms | 6,720 ms | 0 / 16,276 |

**S2 写路径**：p99 72ms 平稳，最长 6.7s 是偶发；瓶颈在 MySQL INSERT + 雪花 ID + Base62。  
**S3 统计查询**：p95 380ms 偏长，源自 MySQL `SUM(clicks) + 7 天 daily` 多行查询；Redis 命中部分较快。  
**S4 跳转未命中**：p90 已经 392ms，前批请求首次 miss → 回源 DB → 写 NULL 占位，**后续请求命中 NULL 占位**才回落到 27ms 附近，长尾属于冷启动期的正常现象。

## 4. 资源占用（全程均值 / 峰值）

| 容器 | CPU 均值 | CPU 峰值 | 内存均值 | 内存峰值 |
|------|---:|---:|---:|---:|
| shortlink-app | 100% | **262%** | 653 MB | 728 MB |
| shortlink-redis | 8% | 31% | 5.7 MB | 6.6 MB |
| shortlink-mysql | 16% | 78% | 379 MB | 381 MB |
| shortlink-kafka | 30% | 133% | 937 MB | 995 MB |

- **App CPU 峰值 262%**（多核累加）= 接近打满；JVM 堆 + 线程栈 + metaspace 共约 728MB，**比 `-Xmx512m` 大出 200MB**，说明非堆区域（主要是 Tomcat 工作线程的栈 + DirectBuffer）在高并发下吃掉了不少内存。
- **Redis** 几乎不参与（缓存命中路径 1 次 GET）；CPU / 内存都极低——**完全没成为瓶颈**，这是这套架构希望看到的结果。
- **MySQL** 峰值 78%（在 S2 / S3 阶段被 `INSERT` 和 `SELECT SUM` 拉起），是 S2 / S3 的实际瓶颈。
- **Kafka** 一直 30%+ 持续占用（事件循环 + LogSegment 维护），是基础开销。

## 5. 关键发现

### 5.1 c=180+ 的连接重置（已复现）

并发 180 之后所有连接立刻被 `RST`，**与 keep-alive / IPv4 / DNS 无关**（均已交叉验证）。`ab` 进程本身 `ulimit -n = 1,048,575` 不是客户端限制。怀疑：

- Spring Boot 默认 `server.tomcat.threads.max=200` + `accept-count=100`，配合默认的 `max-connections` 在 200 并发时**accept 队列溢出**；
- 或容器 ulimit（需 `docker exec` 进容器确认）；
- 或 macOS 本机 `kern.ipc.somaxconn` 对回环连接的隐式上限。

**建议定位步骤**（下次再压时补做）：进容器看 `ulimit -n`、在 `application.yml` 显式设 `server.tomcat.threads.max=400` + `accept-count=200` 再压 c=200。

### 5.2 阶梯并发增益非线性

50→100 +60% RPS，100→150 +16%。**到 150 已经接近本机单实例的天花板**，再压只能换机器。生产环境若需更高 QPS，应该扩多实例 + 负载均衡，而不是把单实例压到极限。

### 5.3 写路径吞吐只有读路径的 1/12

S2 = 530 RPS vs S1@100 = 5,181 RPS。差距来自：

1. **MySQL 同步 INSERT**（每条请求 1 行，事务提交）
2. **雪花 ID + Base62**（纯 CPU）
3. **Redis SET**（热路径走 Lua 不算，但创建路径是多次 RTT）

如果创建是核心业务，可以加本地内存缓冲 + 批量刷库，或异步化落库。

### 5.4 404 路径的长尾可接受

S4 p99=1.26s 来源于：冷启动期未命中 → MySQL SELECT → 写空值占位。空值占位（`__NULL__`）生效后，后续请求 1 次 Redis GET 就能拒绝。**生产上 5 分钟 TTL 足够让热点错误码变成缓存命中**。

## 6. 结论

| 维度 | 评估 |
|------|------|
| 跳转命中稳定性 | ✅ 优秀，c≤150 时错误率 0，p99 ≤ 70ms |
| 单实例吞吐 | ✅ c=150 / 6,000 RPS 仍在线性段，**单实例可承载日均 5 亿次跳转**（按 30% 峰值系数） |
| 写路径 | ⚠️ 530 RPS 够用，**未到瓶颈**但增长空间有限 |
| 404 路径 | ✅ 长尾受限于首次冷启动回源，命中占位后即降为缓存读 |
| 并发硬上限 | ⚠️ **c=180 触发连接重置**（服务侧限制），需配置层面补强 |
| Redis 角色 | ✅ 缓存命中路径下基本不参与，预期符合 |
| MySQL 角色 | ⚠️ 是 S2 / S3 的真实瓶颈（INSERT + 聚合读） |

**适合生产的目标水位**：单实例 **5,000 RPS 读 + 500 RPS 写**（留 20% 缓冲）；若总读 QPS > 10K，水平扩到 2 实例 + 负载均衡即可。
